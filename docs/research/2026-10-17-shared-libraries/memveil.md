## Assessment

The owner's priorities are (1) independent Rust crates, (2) a framework for new scope applications, and (3) language-neutral Rust/C/Mojo reuse later. This lane supplies lessons and future boundary constraints for those priorities; it proposes no Mojo changes now. The strongest existing library boundary is already implemented: Mojo userspace calls a small C/libbpf bridge, while clang compiles C BPF. `libbpf-mojo` owns native objects, links, ring consumers, map adaptation, typed errors, and transport lifetimes; MemVeil owns probe meanings, identities, accounting, external schemas, profiles, privacy, and reports. Preserve that split and the chosen Mojo application. A common Rust application core would add a second ownership/FFI boundary and packaging dependency without evidence that these product-specific reducers agree.

Near-term reuse should be (1) common invariants and regression vectors, (2) versioned evidence/quality schema fragments and compatibility tests, and (3) existing libbpf-mojo native contracts where another consumer actually needs them. A tiny additional C ABI for a demonstrated pure shared operation is viable, but it should neither duplicate the bridge nor carry product event schemas. Keep the existing bridge's native and Mojo APIs independently versioned from any future shared contracts.

## Native bridge and FFI restrictions

The existing native bridge is a viable minimal cross-language adapter, subject to its actual scope:

* The public generic header explicitly targets x86-64 Linux, LP64, little-endian; AArch64 equivalence is unestablished (`native/include/libbpf_mojo_generic.h:3-15`). Do not advertise portability from fixed-width fields alone. Native pointers and alignment still cross this ABI.
* Fixed-width `abi_version`/`struct_size` prefixes, enum discriminants, exact sizes/offsets, span bounds, signed native errors, and output validity are ABI contracts. A Rust wrapper could consume them without moving Mojo application code, but would need its own layout/ownership/negative tests.
* C retains copies of ELF/name/configuration and owns native objects, callbacks, links, rings and staged bytes. Mojo owns mutable caller output. No Mojo objects or arbitrary Mojo callback closures cross the native boundary. Generic views retain native parent references and the dynamic-library handle; close may return `EBUSY`, while release drops the external reference. The library must outlive children, destructor calls, and callable use (`docs/ownership.md:24-82`).
* Single-thread owner semantics and immediate same-thread diagnostic capture apply; an `ArcPointer` keeping a loader alive is not a concurrency qualification. Do not infer `Send`/`Sync`, cross-handle concurrency, or callback thread safety (`docs/ownership.md:18-22`; `docs/mojo-unsafe-inventory.md:29-31,68-71`).
* Negative callback return consumes a libbpf ring record. `ENOSPC` retention works because the adapter copied into an owned slot first. Do not reimplement ring synchronization in Mojo or a new common core (`docs/ownership.md:145-166`; `docs/support.md:126-136`).
* The generic API currently exposes tracepoint attachment; XDP test-run admits its documented restricted result profile. This does not establish coverage for every uprobe/fentry/kprobe need of the other products (`native/include/libbpf_mojo_generic.h:94-96`; `docs/support.md:78-87`).

For an additional shared native component, the safest initial interface is a synchronous, stateless function over bounded bytes plus fixed-width options/result, or an opaque owner with explicit destruction only if state is unavoidable. Avoid allocator ownership transfer, exceptions across FFI, hidden threads, callback-driven application state, borrowed pointers retained beyond a call, or conflation of wire/frame/schema versions. First demonstrate two consumers and independent test expectations; one implementation plus a wrapper is not evidence that all four products need the same runtime.

1.
