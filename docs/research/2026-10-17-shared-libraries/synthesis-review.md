## Findings to resolve

1. **The advertised case inventory omits the central compiler investigations.** `testing-strategy.md:45-79` contains H01-H28, but none specifies the used-result RMW old/new-value oracle, AtomicLoad selection failure, feature-by-feature expanded-v4 emission, or mixed Rust/C debug-record/BTF retention regression. `TODO.md:61-66` and `kernel-toolchain-notes.md:28-52,73` identify these as necessary work; TS1/T01 currently describe a 28-case inventory that can be assigned in full while missing them. Add explicit compiler case IDs with donor paths, independent oracle, negative controls, tiers and toolchain scope, or explicitly define a separately governed compiler inventory. Update case counts and cross-links together. Keep concurrent-map/ordering evidence separate from the preserved single-run stack-memory oracle.

2. **The first milestone has conflicting scope.** `README.md:125,131,149` and `TODO.md:21` select held-image identity + bounded reads, adding process authority only where needed and deferring supervision. `overlap-matrix.md:84-87` calls full process authority and finite supervision order 1, ahead of held-file/image inspection; `TODO.md:38` also makes first migration depend on L05's owned-child cleanup work. This can unnecessarily make the narrow library depend on the documented SIGCHLD/pre-exec/global-registry hazards. Align the ordered table with the chosen image slice; make L05/L06 prerequisites conditional on actually extracting supervision. Keep the small process-observation authority subset explicit where image acquisition needs it.

3. **Build-support package creation is both mandatory and conditional.** `kernel-toolchain-notes.md:69` says to create a build-support crate, and `overlap-matrix.md:74,91` specifies a package; `README.md:63` says tools/testkit first and a separate crate only when justified by multiple consumers, while `TODO.md:65` says "if needed." Use the conditional wording consistently. The compiler/object corpus is required; a separate public Cargo package is an implementation decision.

4. **Backlog test identifiers do not resolve.** `TODO.md:5` refers to R01-R28; the actual rows are H01-H28 at `testing-strategy.md:52-79`. Correct the prefix, then preserve stable IDs when adding compiler cases. Links between a work item and an acceptance case should be explicit enough to prevent orphaned requirements.

## Refinements

- **Make the private-stack negative gate kernel-specific.** `testing-strategy.md:60` says removing the workaround "must trigger failure." An actual repair in a later kernel may make that a successful removal experiment. Require the object mutant to fail the current workaround checker, and require the live mutant to reproduce corruption only in the pinned affected environment (or label non-reproduction inconclusive). A fixed-kernel control should permit safe removal after the independently expected workload and remaining gates pass.
- **Avoid turning every corpus item into every crate's release gate.** `testing-strategy.md:151` permits explicitly excluded cases, but the "28 required scenarios" heading and broad TS2/T01 wording can obscure that. State that each selected component owns its relevant case subset and the corpus retains the other cases; independent host libraries should not wait for unrelated DMA/FFI/live-kernel work. `TODO.md:3` and the existing feature-specific tier rules already support this interpretation.
- **Pin the particularly recommended BTF comparator.** `external-comparison.md:19,41` makes btf-rs a prominent candidate, but `external-sources.json` has no btf-rs observation. Add an immutable source/release reference or explicitly defer source/API comparison of that candidate to B04. This is reproducibility debt, not evidence the recommendation is wrong.
