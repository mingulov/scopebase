### 1. BPF CPU v1-v4 is a versioned compiler contract

**Historical source:** `W/llvm-bpf-toolchain-experiment.md:77-110`; detailed independent source/ancestry review `W/sdd/p11scope/SYSTEM-PLAN/task-bpf-v4-baseline-review.md:54-83`. The latter was originally advisory and gained an addendum resolving its initially unknown Gotox introduction. Read the addendum before repeating the earlier uncertainty.

Freshly checked [LLVM 18.1.8 subtarget](https://raw.githubusercontent.com/llvm/llvm-project/llvmorg-18.1.8/llvm/lib/Target/BPF/BPFSubtarget.cpp) versus [LLVM 23.1.2 subtarget](https://raw.githubusercontent.com/llvm/llvm-project/llvmorg-23.1.2/llvm/lib/Target/BPF/BPFSubtarget.cpp): generic/v1 takes the baseline; v2 enables extended jumps; v3 adds JMP32 and ALU32; the original v4 bundle adds signed loads/moves, unconditional byte swaps, signed division/remainder, long direct jumps and immediate stores. The newer v4 preset additionally enables acquire/release loads/stores and indirect jumps. Empty CPU and explicit `generic` are different in LLVM23: empty selects v3, generic takes v1. Record effective arguments rather than infer them from package versions.

The retained review pins original-v4 support in both Linux6.9 verifier and x86 JIT at **`a38297e3fb012ddfa7ce0321a7e5a8daeb1872b6`**. This is a positive support observation, **not** a claim all six instructions first appeared in 6.9. It records acquire/release handlers in inspected 6.15 sources and the x86 Gotox introduction **[`493d9e0d608339a32f568504d5fd411a261bb0af`](https://github.com/torvalds/linux/commit/493d9e0d608339a32f568504d5fd411a261bb0af)**, ancestor of 6.19 (`05f7e89ab9731565d8a62e3b5d1ec206485eeb0b`) but not 6.18. Those precise release boundaries are **retained source/ancestry findings**; pinned raw-source rechecks hit web errors/HTTP429 in this turn. They are not new runtime qualification.

**Shared ownership:** a versioned build-profile manifest and final-object instruction inventory, with backend revision, explicit CPU/features, architecture and required kernel semantics. Add minimal owned capability probes and an exact-artifact load/behavior matrix. Keep ISA forms, helper/map/kfunc availability, attach support and CO-RE shape requirements as separate fields. [The ISA specification](https://docs.kernel.org/bpf/standardization/instruction-set.html) defines optional conformance groups; a single “v4 supported” boolean loses necessary information.

**Missing work:** no new whole-application kernel6.9/6.15/6.19 validation was done; no portable non-x86 guarantee follows. Kernel backports/configuration and privilege failures need explicit outcomes. Do not raise an application's kernel floor merely to repair compiler output.

### 2. Used-result atomic RMW miscompile: accepted instructions, wrong behavior

**Historical source:** `W/llvm-bpf-toolchain-experiment.md:46-75`, `W/docs/superpowers/plans/2026-08-18-slice1b2-open-issues-research-plan.md:594`, and `W/evidence/llvm-toolchain-review-20260922/kernel-oracle/` (`cases.json`, `prepare.py`, runner and per-compiler `runtime.json`). The preserved 28-case oracle used owned unattached socket filters and `BPF_PROG_TEST_RUN` on x86 kernel7.0.0-31, checking both returned old value and updated memory. This was functional single-run evidence, not a concurrent-map or ordering qualification.

LLVM18/v3 compiled 24 cases and all 24 passed; LLVM21/v3 and pristine LLVM23/v3 passed 17/24; their v4 cells passed 21/28. The seven failures were used-result i32 add/sub/and/or/xor and i64 add/sub. Stored values were correct and the verifier accepted the programs, while returned old values were wrong. The private LLVM23 patch passed all compiled cases. Unused-result and CAS controls are essential counterexamples to an overbroad “all atomics broken” diagnosis.

**Fresh upstream correction:** the September note's “PR open/unmerged” wording is now historical. [LLVM PR210371](https://github.com/llvm/llvm-project/pull/210371) merged **2026-10-13**, commit **[`9d18ac3e726403b493a54079d5c760f36db33244`](https://github.com/llvm/llvm-project/commit/9d18ac3e726403b493a54079d5c760f36db33244)**; it changes BPF instruction patterns and `llvm/test/CodeGen/BPF/atomics_mem_order_v3.ll`. [Issue210280](https://github.com/llvm/llvm-project/issues/210280) is closed. This does not establish inclusion in installed Rust/bpf-linker binaries or validate the separate load bug.

**Shared ownership:** compiler regression fixture suite, emitted raw-encoding checks, and an independent runtime old/new-value oracle. P already enforces CAS plus unused-result 64-bit atomic adds at `crates/ebpf/native/stop_gate.h:39`, `instance_epoch.h:98` and `scripts/check-stop-gate-object.py:263,600`. Carry semantic restrictions and exact lowering tests together; source spelling alone is insufficient. Revisit restrictions only against the actual selected fixed backend and final mixed-language object.

### 3. AtomicLoad selector failure: compiler feature gate, not kernel rejection

**Historical source:** `W/llvm-bpf-atomic-load-report.md:18-114`; minimal IR is `load atomic i64 ... monotonic, align 8`. Direct llc reproductions remove application, loader and kernel entirely. LLVM18 fails generic/v3/v4; LLVM21 and pristine LLVM23 fail generic/v3 but v4 lowers to an **ordinary u64 load**. Disabling v4's acquire/release feature makes that relaxed load fail selection again. The pattern is gated by `BPFHasLoadAcqStoreRel` in the inspected backend. Do not claim this tiny successful output itself requires a kernel acquire-load opcode.

The report also records bpf-linker0.10.4 rejecting v4 at CLI parsing, before LLVM, and Rust nightly `e50aa6fba4e63ab34c72bf9acfd2c307c1155d1a` actually using LLVM22.1.4, distinct from native Clang18. The draft says unsubmitted; no fresh comprehensive search established this separate bug's current upstream resolution.

**Shared ownership:** minimal C/IR/Rust fixtures with explicit compile-success/refusal expectations, backend feature masks and decoded output. Keep compile diagnostics distinct from kernel load errors. Do not replace atomic semantics with volatile access as a generic repair.

### 4. Mixed Rust/C linker debug-record repair

**Historical source:** `W/llvm-bpf-toolchain-experiment.md:133` onward and `W/sdd/p11scope/SYSTEM-PLAN/task-llvm23-{pipeline-debug-review,linker-repair-report,linker-repair-review}.md`. The actual Rust invocation supplied `--cpu generic`; an earlier fingerprint-based assumption missed it. Original and patched LLVM23 both hit `Expected inlined-at fields to agree` after bpf-linker sanitation, while pre-sanitation IR compiled. Parser-based replay could silently discard invalid debug metadata and still exit zero without BTF/BTF.ext.

Private linker repair **`4727b154a014dd74b9cceb038c365b058f48a53a`**, based on bpf-linker0.11.1 **`24ccdfd47d0627f2dd88066e26a51526dac14cc4`**, is retained at `W/evidence/llvm-toolchain-review-20260922/bpf-linker-repair/0001-Repair-LLVM-23-debug-record-sanitation.patch`. It preserves debug-record scopes and verifies the live module across transformations. The report ultimately records both full BPF variants building with BTF retained, while application loading/behavior/kernel matrix/performance gates remain. The experiment remains parked rather than adopted by that record.

**Shared ownership:** build helpers selecting native compiler, Rust compiler, linker and the LLVM library actually loaded; minimal metadata fixture and required-section checks. Upstream status of this private linker repair was not refreshed; do not assume it became unnecessary when the atomic PR merged.

## Extraction recommendation

Create a first-class **compiler workstream**, a **BPF object/compatibility regression kit**, and a **versioned compatibility document/data set** before a larger runtime framework. Start immediately with tools/testkit and shared host Rust modules; publish a separate build-support crate only when two concrete build callers establish a reusable API, initially p11scope and KryProbe. Separate generic mechanisms from each application's rule manifest. Reuse existing Aya/object/BTF implementations and upstream fixtures; avoid another unrestricted loader by default. A product adapter names its minimum supported configurations, maps, native ABI, programs, privacy constraints and behavioral oracle. [H29–H32](testing-strategy.md#hard-regression-matrix-32-scenarios-with-component-specific-gates) are the explicit new compiler cases; [C01–C06](TODO.md#f2-bpf-support-and-compilerkernel-compatibility) govern delivery.

Acceptance should cross five independent layers: (1) native/Rust source and IR compile; (2) effective linker/backend and final ELF/BTF/instructions; (3) loader relocation/map/call interpretation; (4) actual kernel verifier/JIT acceptance; (5) behavior under independently known populations and relevant concurrency. Passing one layer does not establish the next. Shared tooling should return precise outcomes for compile refusal, malformed artifact, unsupported capability, permission denial, verifier rejection, incorrect execution and unknown status.

Missing high-value regression coverage includes final mixed Rust/C objects through the fixed upstream atomic backend, concurrent shared-map RMW/CAS old-value oracles, exact-artifact oldest-kernel lanes, feature-by-feature v4 emission, metadata-retention negatives, and private-stack workaround removal controls. These are proposed shared work, not claims that every product lacks every test. Keep host-only models, historical receipts, source support and freshly reproduced runtime behavior distinct.
