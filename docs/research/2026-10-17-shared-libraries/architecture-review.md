# Independent architecture review

2026-10-17. Static review of README, TODO, external comparison, overlap matrix, testing strategy, kernel/toolchain notes and the cited donor research. No implementation approval, product edits, builds or tests. “Blocking” below means correct before converting this proposal into an implementation plan, not that research must stop.

**Verdict:** proceed with independent Rust mechanisms and their regressions, then an SDK, then selected C/Mojo reuse. p11scope + OSSLscope remain the right first acceptance pair. The first useful library is feasible, but its boundary must be smaller than the aggregate `scopebase-linux` description. Compiler compatibility is a first-class parallel workstream immediately; publishing an additional initial crate is a separate decision.

## Blocking corrections

### A1. Define the first slice as held-file acquisition and bounded inspection

README:125,131 is sound if “image identity” means an owned file capability plus explicitly scoped evidence. Do not begin with the whole p11scope discovery identity implementation or with a universal `PinnedImage` guarantee. p11scope's product module incorporates manifest trust, overlay heuristics, budgets and retained mapping proofs; its metadata checks expressly are not a security boundary. OSSLscope's file primitive is cleaner, but its mtime/length checks likewise do not prove immutable contents. See [P4/P12 and fixes](p11scope.md#recommended-boundaries-12-candidates), [O4–O6](osslscope.md#o4-descriptor-bound-attachment-identity-and-stable-physical-cookies).

Recommended first API responsibilities: acquire/check a regular held file without reopening an untrusted pathname; read under caller-supplied byte limits; return retained bytes and separately typed descriptor/stat evidence; expose the same owned object to the consumer's attach adapter. Keep ELF parsing behind the consumer's existing parser initially. Name identity domains explicitly and leave content immutability, current-mm continuity, cache relevance and provider classification outside the guarantee.

Use OSSLscope `src/plan.rs` (`PinnedFile`, `ReadBoundedSource`, `read_bounded_from`) and p11scope `crates/manifest/src/identity.rs` (`open_regular`, `inspect_file_with_reader`) as selected file-level donors. Pin those files and their tests, rather than treating either active integration HEAD as a qualified release. p11scope's unrelated H8/H9 journal drift is a custody concern, not a reason to reject stable selected file mechanisms; its initial research pin is `fb81ee74b5c185d8abaef1cd93b168d6c241989e`.

Mapping calibration must be optional and explicit. p11scope's private self-mapping can interfere with watched-file attachment/cleanup; preserve no-new-mapping mode, held-proof reuse and the possibility of inconclusive evidence. Btrfs/overlay tests remain mandatory for any advertised maps-domain adapter, but that adapter need not ship in the first file-only release. Do not silently “fix” OSSLscope's stat-domain semantics by replacing it with a maps-domain integer. [P filesystem fixes](p11scope.md#hard-fixes-worth-carrying-with-their-regressions), [overlap rows 03–05](overlap-matrix.md#support-and-applicability-matrix).

### A2. Make attachment retention an explicit cross-crate ownership contract

The first slice needs a documented handoff to the BPF adapter even if attachment stays product-local. OSSLscope currently relies on link-before-pin field destruction; p11scope must retain the original file during pending/failed asynchronous retirement. “Owned FD” alone is insufficient if the caller can drop it while a link or cleanup job remains. [O4](osslscope.md#o4-descriptor-bound-attachment-identity-and-stable-physical-cookies), [P7](p11scope.md#recommended-boundaries-12-candidates).

Require the attachment owner to retain the file capability through detach or explicit unresolved quarantine; successful construction cannot imply synchronous successful destruction. Keep Linux ownership below the BPF layer, with attachment adapters owning both resources, avoiding a reverse dependency from `scopebase-linux` to Aya. Carry H04/H19 loss-of-ownership and cancellation tests into every adapter that claims this lifetime, rather than accepting a field-order comment as the reusable API contract.

### A3. Resolve compiler packaging separately from compiler priority

[README:63](README.md#suggested-name-and-packaging) says tools/testkit first; [kernel note:69](kernel-toolchain-notes.md#extraction-recommendation) mandates a build-support crate; [overlap transfer 8](overlap-matrix.md) also names a package. Use the README rule consistently: a first-class compiler workstream now, initially shared Rust modules plus tools/testkit and versioned compatibility data; publish a build-support crate when two build callers demonstrate a stable reusable API. Do not interpret “tools first” as postponing this work until after attachment extraction.

p11scope's Cargo/rustc/sysroot pairing and dual-output-directory isolation are already credible small mechanisms; KryProbe's bounded build/retry path is a useful second caller. OSSLscope's placeholder build.rs is not evidence of a reusable build API. A crate can be justified early if those two integrations actually happen; it must remain an ordinary host Rust dependency with explicit tool invocations, no automatic nightly installation, and no selected product compiler pins embedded as universal policy. [P10](p11scope.md#recommended-boundaries-12-candidates), [K11](kryprobe.md#11-bpf-object-hygiene-and-compiler-regressions--extract-teststools-upstream-where-suitable), [overlap row 25](overlap-matrix.md#support-and-applicability-matrix).

Make an artifact manifest the cross-project interface: actual compiler/backend/linker identities, CPU/features, generated instructions, BTF/relocation checks, named kernel cells and independent semantic outcomes. This transfers to C/Mojo without binding those projects to Rust command construction. Selecting the right LLVM shared library and proving correct lowering remain separate checks.

### A4. Add explicit regressions for the newly recovered LLVM findings

The 28-row matrix predates the exact investigation. H08/H10/H14 do not explicitly cover its distinct failures. Extend it with separate cases for: (a) version-dependent CPU-preset expansion versus final emitted instruction contract; (b) used-result atomic RMW checking both old return value and changed memory, widths and unused-result/CAS controls; (c) AtomicLoad instruction-selection failure under the selected CPU/features; (d) mixed Rust/C debug-record transformation retaining valid BTF/BTF.ext. Link these directly to C01–C04 and the [exact investigation](kernel-toolchain-notes.md#strongest-match-to-the-remembered-investigation).

Keep compile, final-object, loader, verifier/JIT and runtime verdicts separate. LLVM PR 210371 does not repair the distinct selector/linker failures or prove the installed Rust backend contains its fix. Historical single-run atomic success does not establish concurrent-map ordering. The testkit must exercise the final consumer build path, not only clang or an intermediate IR file. Correct TODO:5's `R01–R28` references to the matrix's actual `H01–H28` IDs while adding the new cases.

### A5. Scope acceptance dependencies per component without weakening tests

TODO L07 currently depends on L05's full owned-child cancellation/stalled-setup contract, although README:131 defers lifecycle transports. T06 depends on B02 attachment and Q04 capture integration even for an independent file library. T05 depends on all T01–T04 work. Those edges make the stated small-first approach accidentally depend on later subsystems. [TODO L05–L07, T05–T06](TODO.md).

Replace blanket edges with selected-contract prerequisites. A file-only first release needs H04/H06 and relevant FD/cap/ownership tests, two real consumer integrations, standalone packaging and resource budgets; maps-domain support adds H05, actual attachment adds its live H04/H19 obligations, and child custody adds H02/H20. A host-only library does not need an unrelated BPF compiler fix to release. Conversely any BPF instruction/support claim must pass the corresponding new compiler cases before publication. This preserves strong evidence while allowing genuinely independent crates.

## Optional changes and retained decisions

- Keep the proposed package count provisional. Start with one host Linux package and a shared test/tool repository area; add BPF and capture packages when their consumers exist. BTF remains a module or dependency adapter until a separate API/consumer boundary warrants a crate. Testkit should not become a production runtime dependency. [README packaging](README.md#suggested-name-and-packaging).
- A low-risk parallel milestone is shared bounded attachment planning over upstream Aya multi-uprobes, preserving product-supplied error policy. p11scope halts selected errors while OSSLscope salvages RHEL errno 524; centralize attempt bounds and rollback ownership without replacing both policies with a global errno table. Do not make raw syscall wrappers or the restricted OSSLscope loader the shared platform. [P1](p11scope.md#recommended-boundaries-12-candidates), [O7–O9](osslscope.md#o7-raw-bpf-syscalluapi-bindings-and-functional-feature-diagnosis), [external comparison](external-comparison.md#upstream-multi-uprobes-already-exist).
- `scopebase-capture` is plausible after concrete adapters, but start with units, scoped tokens and checked conservation helpers. A common quality lattice, terminal enum or serialized schema can accidentally equate incompatible evidence. Keep OSSLscope's delayed-hit countermodel, KryProbe's architecture-bound fence and MemVeil's open live settlement visible in conformance. [Overlap rows 12,15,19,20](overlap-matrix.md#support-and-applicability-matrix).
- Retain all-ref/WIP/document provenance as the donor-selection process, not a requirement to merge every divergent branch. For each promoted mechanism choose a selected source pin plus any explicitly adopted WIP patch and regression; documentation-only counterexamples can invalidate a proposed guarantee even when they contribute no code. Existing census qualification is appropriately cautious.
- Keep per-file licensing/provenance an initial design input. “Independent general Rust library” describes usability, not an implied permissive license or permission to unify donor notices. Existing dependencies should replace lower-level plumbing only after the donor-specific regressions prove fit. [External proof of fit](external-comparison.md#proof-of-fit-before-adopting-or-replacing-a-dependency).

The next design should approve a precise held-file/bounded-read contract and two migration seams, alongside the immediate compiler-corpus workstream. It should not approve a universal process identity, shutdown engine, loader or framework by implication.
