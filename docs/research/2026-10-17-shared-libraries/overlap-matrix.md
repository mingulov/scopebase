# Cross-project overlap, support gaps and transfer opportunities

Research synthesis, 2026-10-17. This combines the four source investigations and [external comparison](external-comparison.md#main-finding); it adds no builds, runtime tests, implementation, support claim or upstream action. Repository pins, branch/worktree coverage and WIP custody remain in [p11scope](p11scope.md#revision-and-authority), [KryProbe](kryprobe.md#revision-and-custody), [OSSLscope](osslscope.md#source-custody-and-current-state), and [MemVeil/libbpf-mojo](memveil.md#revision-and-custody-boundary). “Current” means those inspected source snapshots. An implementation on an unqualified candidate is still code, but is not an accepted runtime guarantee.

The main overlap is **contracts around existing operations**: process/image authority, exact map geometry, provenance, loss units and the evidence required to close a window. The applications should share these small contracts and their regression cases while retaining their domain reducers. Existing Aya/libbpf, object/goblin, procfs/rustix/pathrs, and potentially btf-rs/blazesym remain underlying implementations to evaluate, not dependencies to install together.

## Evidence labels

- **C — code+test-source:** the repository note identifies implementation and relevant regression source. Tests were inspected, not run by this study; this label does not imply complete coverage or live qualification.
- **L — partial/limited:** implementation exists but only covers the named subset, model, architecture, consumed dependency revision or incomplete lifecycle proof.
- **D — doc/WIP-only:** the particular claim is documented/proposed or belongs to a still-changing work lane; any implemented subpiece is named separately.
- **NA — not-applicable:** outside that product's present mechanism/domain. This is not a statement about future utility.
- **NE — not-established:** the inspected notes do not establish this capability. This is an evidence gap, never an assertion that the source lacks it.

## Semantic boundaries that must survive sharing

1. **Birth is not exec.** A pidfd/starttime pair can identify a process lifetime while its image changes. Poll-observed TID births are weaker than producer task-storage identities. Session/boot/namespace/map domains are independent dimensions; process tokens must not be accepted as image tokens.
2. **Stat, maps and BTF identities are different.** File inode/device custody, kernel-rendered mapped-device identity and kernel type/layout provenance answer different questions. A single hash or device integer must not substitute for all three. Holding an inode does not freeze its contents.
3. **Batch decode is not a live controller.** Share decoder and evidence invariants; live owns sensors, admission, clocks, cancellation and tails. Preserve KryProbe ADR-0007's intentional split and each consumer's multiplicity rules.
4. **Execution context is not causal origin.** Current task/cgroup, insertion-time identity, request submitter and eventual callback executor may differ. Unknown origin must remain unknown; temporal proximity and a successful metadata lookup do not establish a causal edge.
5. **A point snapshot is not final settlement.** Fixed ring boundary, empty poll, frozen admission, writer quiescence and sample-after-drain are different evidence strengths. OSSL's delayed-hit countermodel and MemVeil's unwired live settlement prevent a universal “complete” bool.
6. **Exact counters, capped flags and view quality are different.** KATTRLOSS is capped diagnostic evidence; a detail drop need not invalidate an aggregate counter, and a report-local partial view must not erase historical facts or reset persistent losses. Carry units, population, epoch, scope and reason.

## First Rust boundaries, then application SDK, then native consumers

These are provisional module boundaries, not final package names or commitments to implement all six at once. Their order follows the main proposal; compiler tooling starts alongside the first file slice. The twelve transfers above rank opportunities within this larger inventory, not prerequisite implementation milestones.

|---|---|---|
| **1. Held-file acquisition and bounded inspection** | Retained regular-file capability, bounded retained bytes and separately typed stat evidence; keep existing consumer parser. Attach adapter retains the file through detach or explicit unresolved quarantine. | P + O first; K later uses executable pin subset. H04/H06 plus relevant FD/cap controls. A later SDK may compose those libraries into capture/report/doctor/testing seams after at least two real Rust applications use them without semantic escape hatches. It should not merge batch and live controllers, require identical event schemas, impose one privacy allowlist, or centralize all domain state machines. SDK readiness is a separate milestone from shipping any one library.

C/Mojo reuse follows demonstrated demand: prefer neutral fixture/schema contracts first, then a narrow fixed-width synchronous ABI or opaque owner around an actually shared operation. Preserve libbpf-mojo's existing single-thread ownership, parent/library lifetimes and tracepoint attachment scope; a Rust core is not a prerequisite for MemVeil. [MojoBPF](memveil.md#mojobpf-limited-future-integration-reconnaissance) is a later compiler/artifact and native-consumer lane: it already produces standard BPF ELF through a matching LLVM adapter, while MemVeil uses Mojo userspace with C BPF. Neither architecture needs a rewrite to participate.

## Follow-up evidence before claiming coverage

Recipient NE cells should become a bounded source/test investigation or a selected adapter spike, not a defect ticket by assumption. Each promoted shared primitive needs a donor regression that fails a plausible broken version, a second consumer with its own expected population, exact source/object/toolchain pins, and explicit host/model/verifier/live evidence. Preserve licensing/provenance per file; shared mechanism similarity does not establish permission or compatibility. The [external proof-of-fit checklist](external-comparison.md#proof-of-fit-before-adopting-or-replacing-a-dependency) and the separate testing-strategy deliverable govern validation detail.
