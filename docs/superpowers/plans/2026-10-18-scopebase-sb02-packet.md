## Explicit approval authority and immutable Cargo inputs

The two tools receive all build-policy authority from their **named, hashed matrix**: per-case/member `allowed_dependencies` plus that matrix's top-level `approved_build_inputs`. Neither tool searches another matrix, infers permission from the source inventory, accepts a prior successful compile as approval, or populates approval records automatically. Source availability is not execution permission. A package with a build script and/or proc-macro target must both appear in the case/member allowlist and match the applicable approved record before any Cargo compilation. A normal library dependency also requires an exact allowlist entry. Internal trusted probe/fixture source is bound by matrix/source hashes and inspected for local build scripts; a local script fixture requires its own explicit approved record. For that record only, `source` is `fixture:<member-id>` and `sha256` hashes the deterministic compact JSON/newline sorted list of `{path,sha256}` for every checked-in regular file under that fixture's root, excluding generated Cargo targets/outputs that cannot reside there. Resolve the fixture from that matrix's exact member manifest, not an ambient path. Archive normalization is a recorded Cargo transformation; recheck executable source and manifest/build-target semantics against the approved original before executing the unpacked fixture.

`sha256` in an allowlist/approval record means the exact registry archive digest, or for an acquired path package the deterministic package source digest defined in the input inventory below. The build-script approval is exact by package name/version/upstream source/digest and script path. A proc macro without a script uses `build_script:null`; a package with both requires the script path and its approval reason must explicitly cover both code-execution roles. Role checks inspect Cargo target kinds and dependency kinds, not the recorded label alone. An approved record for another package version, source or case-unreachable package grants no access. Duplicate conflicting approval keys are schema errors. Both matrices may intentionally duplicate an identical reviewed record without sharing mutable configuration.

The executor can draft narrow source-review reasons for ordinary Rust cfg/version generators and inspected proc macros, as previously authorized. The controller/reviewer evaluates those records with the candidate. Unknown/native/BPF/tool-download behavior remains NEEDS_DECISION. The CLI cannot create an approval simply because a package is needed. A dependency resolution report is deliberately not a permission token.

## Report and verdict contract

Both tools write one UTF-8 JSON report atomically to `--report`, with trailing newline. Detailed bounded stdout/stderr are private files referenced by digest. Stdout is one short JSON summary with `report`, `status`, `counts`; stderr is bounded actionable diagnostic text. No raw source/workspace secrets are included in diagnostics.

Top-level report keys: `schema_version:1`, `tool`, `cargo_inputs_sha256`, `staged_inputs` (records defined in the staging sequence above), `scope` (`full` or `selected_cases`), `matrix_sha256`, `manifest_sha256` (null only where not applicable), `product_base`, `toolchains`, `rows`, `summary`, `product_qualification:false`. Toolchain records include actual rustc `-Vv` and Cargo version plus executable digest. Each row has `id`, `role`, `required`, `toolchain`, `phase`, `status`, `fit`, `reason_code`, `expected`, `observed`, `command`, `cwd`, `input_sha256`, `lock_sha256`, `resolved_packages`, `resolved_features`, `logs`, `duration_ms`, `cleanup`. Nullable fields remain null for stages not reached; no invented lock or command. `status` is PASS/FAIL/BLOCKED/NOT_RUN; `fit` is SATISFIED/GAP/UNKNOWN/NOT_APPLICABLE. `cleanup` is `complete`, `unresolved`, or `not_started`.

Examples: public BTF parse can PASS/SATISFIED while exact-ID privacy refusal PASS/GAP establishes that the broader API contract is absent. Duplicate-key last-wins behavior may be a PASS/GAP observation, never successful strict replay. A missing comparator is BLOCKED/UNKNOWN with `SOURCE_UNAVAILABLE`, not a failed API or an optional skip. Negative controls record the intended inner rejection plus outer sensitivity test; the actual mutant must be rejected at the named assertion. A root empty-workspace row is PASS/NOT_APPLICABLE with `CONFIGURATION_ONLY` and `real_members:0` in `observed`.

Summary status precedence: FAIL if any required assertion/policy/control fails; otherwise BLOCKED if any required row is BLOCKED/NOT_RUN or cleanup unresolved; otherwise PASS for the selected **tool/probe scope only**. Selected-case execution reports omitted required IDs and full-matrix completeness false. Counts include all required IDs, including unavailable ones. A verified observed GAP is an executed result but prevents automatic primary selection; `summary.decisions_required` lists those cases. No checker output sets SB02 or any component task complete.

Exit 0 means all required rows of the requested scope met their expected assertions/policy, with any fit gaps explicitly listed; exit 1 means an assertion/policy failure; exit 2 means malformed input or usage; exit 3 means required unavailable/incomplete execution. Mixed failure/incomplete uses exit 1 plus both in JSON. The caller must read `scope`, `fit`, and `decisions_required`; exit 0 alone never grants dependency adoption. Unexpected exceptions produce a bounded INTERNAL_ERROR failure, not a fabricated passing partial report.

## Build policy algorithm, in order

1. Validate schemas/paths and enumerate root members using metadata without building. Inspect fixture/product manifests and Cargo configuration files before invoking Cargo. Explicitly inspect ordinary/dev/build dependencies, target-specific dependency tables, workspace-inherited dependencies, `[patch]`, `[replace]`, default/optional feature wiring, `build` and automatic `build.rs` detection. Reject undeclared path overrides and external/sibling paths even if optional or target-specific; no default-feature escape. Approved internal workspace package edges may exist for future real products, but must carry package name/version for packaging and be explicitly registered. A path into any donor is always rejected.
2. Use an isolated owned Cargo home/configuration and the exact installed rustc/rustdoc/cargo paths. No inherited `RUSTC_WRAPPER`, `RUSTC_WORKSPACE_WRAPPER`, `RUSTFLAGS`, `RUSTDOCFLAGS`, `CARGO_ENCODED_RUSTFLAGS`, target runners/linker overrides, or user configuration may silently affect a run. Reject unexpected relevant Cargo/Rust overrides or explicitly clear and record them. Stage exactly the `cargo_inputs` inventory using the pinned Cargo fetch/vendor and frozen-copy procedure above; no implicit Cargo home/index/cache input exists. No global config/cache writes or wholesale cache copies. Missing offline closure returns BLOCKED. Explicit acquisition and nonexecuting resolution precede closure approval; compilation follows both.
3. Generate one independent lock per probe or external minimal/default/union workspace using Cargo 1.88.0. Preserve it; use the same lock with 1.98.1. Run `cargo metadata --offline --locked --format-version 1 --filter-platform x86_64-unknown-linux-gnu` for the exact feature selection. Capture resolved IDs/features/dependency kinds and compare declared candidate pins and allowlists. Use no `--no-deps` for closure validation. Metadata alone never runs a build script; a resolver failure must not be relabeled policy rejection. Conservatively inspect every resolved manifest, including build and proc-macro inputs; record the over-approximation rather than claiming disabled edges executed.
4. Before **any** compilation, reject forbidden packages/`links` native requirements and any unapproved custom-build/proc-macro closure. Identify custom-build targets from metadata, not string searches for `clang`. A new `build.rs`, `build = "other.rs"`, changed approved source, alias package, transitive script, optional activation or target table cannot bypass this gate. Verify extracted source against the admitted immutable package digest. An otherwise admissible but unapproved script is BLOCKED/APPROVAL_REQUIRED and is not executed; a forbidden package/native/BPF requirement is FAIL/POLICY_REJECTED. Negative-control tests assert the specific inner refusal and nonexecution marker, not just any nonzero exit. Rust-only scripts are permitted only by their exact reviewed input record. This is a source admission policy, not a claim of arbitrary runtime confinement.
5. Package the subject into its private target output. Run `cargo package --list` with exact manifest and lock and compare the normalized set to `package_files`; reject any unexpected private research/provenance/credentials/donor path. Run `cargo package --no-verify --offline --locked --allow-dirty` only in the isolated copied source tree; unpack the resulting archive safely (no absolute/traversal/symlink escape), verify names and digest, and rerun manifest/closure policy there. `--no-verify` is intentional: verification is performed by the actual downstream jobs below and must be reported separately. No publish/install occurs.
6. Build external workspaces against the unpacked archive using a single generated exact subject path dependency. This is the checker's explicit controlled subject edge, not permission for packaged dependencies to use sibling paths. Check that the subject package's normalized manifest has no residual donor/sibling dependency. Every external workspace has its own root/lock; no registry patch to the repository or donor. Later real multi-package releases need a separately approved staged registry/vendor closure; do not auto-allow sibling paths to make them pass.
7. For each compiler, run `cargo check --offline --locked --all-targets`, `cargo test --offline --locked --lib --tests`, and explicit `cargo test --offline --locked --doc` on the relevant packaged subject/probe with the exact feature selection. Doctests run on the subject package itself: downstream `cargo test` does not execute dependency doctests. Run each client binary's assertions. Test minimal/default configurations independently and the two-member client workspace for each supported union. Assert one subject package ID/version/source, observed feature union and expected closure; no second separately resolved subject copy can certify the first.
8. Report each stage even if later stages cannot run. Fail closed on missing members, missing doctests for the fixture that is designed to contain them, absent positive controls, unexecuted client assertions, or incomplete package inspection. Keep product readiness false until real component owners supply their own client/contracts and delivery evidence.
